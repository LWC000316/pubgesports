# e스포츠 실시간 데이터 자동 최신화 파이프라인의 타당성 및 잠재적 오류 분석 보고서

## 1. 개요 및 분석 목적

공식 PUBG API(`https://api.pubg.com`)를 기반으로 한 데이터 자동 추출 및 최신화 파이프라인이 향후 어떤 대회(PWS, PCL, PGS, PGC 등)에서든 무결점 상태로 완전 자동화가 가능한지, 과학적 객관성에 기반하여 발생 가능한 잠재적 오류 요인과 한계를 전수 평가합니다.

## 2. 자동 최신화가 완벽히 보장되는 영역 (성공 요인)

* 공식 대회 인게임 수치 데이터의 무결성:
  * 킬 수, 입힌 데미지량, 넉다운 수, 순위, 생존 시간, 사용 무기 통계 등은 게임 서버 로그에서 직접 생성되므로 100% 신뢰성을 가집니다.
* 실시간성:
  * 크래프톤 공식 e스포츠 샤드(`tournament`)에 등록된 경기는 매치가 종료되는 즉시 세부 통계와 텔레메트리(Telemetry)가 적재되므로 가장 빠른 최신화가 가능합니다.
* 재현 가능성:
  * 각 매치마다 전 세계 고유 식별자(UUID)가 부여되므로 언제든 동일한 원시 데이터를 검증할 수 있습니다.

## 3. 발생 가능한 잠재적 오류 및 구조적 한계점

### A. 닉네임 기반 팀 태그 분리(Prefix Parsing) 오류
* 현상:
  * 현재 파이프라인은 선수 닉네임의 언더바(`_`) 또는 공백 앞부분을 팀 태그로 파싱합니다 (예: `GK_AKaN` -> 팀 태그 `GK`).
* 잠재적 오류 시나리오:
  1. 선수 닉네임 자체에 언더바가 포함된 경우 (예: `TEAM_ALPHA_PLAYER`의 경우 팀명이 `TEAM`인지 `TEAM_ALPHA`인지 모호).
  2. 팀 태그 없이 본인 소환사명만 사용하는 용병 선수나 계정 변경 선수 발생 시 개인 단위로 팀이 쪼개져 16개 이상의 팀으로 잘못 집계될 위험.
  3. 클랜명과 프로팀명이 혼용되거나 스폰서 태그가 접미사(Suffix)로 붙는 경우 파싱 실패.

### B. 팀 리브랜딩 및 스폰서십 변경의 지연 (Qx -> HSD 사례)
* 현상:
  * 선수가 인게임 닉네임을 바꾸지 않았거나, 공식 API 대회 계정이 이전 팀명으로 등록된 상태에서 대회 직전 팀명이 변경되는 경우.
* 잠재적 오류 시나리오:
  * 크래프톤 API는 인게임 텍스트 문자열 그대로를 반환하므로, 실제 현실에서 발생한 리브랜딩, 팀명 인수, 스폰서십 계약을 API 자체만으로는 자동 감지할 수 없습니다.
  * 별도의 메타데이터 매핑 테이블 없이는 사용자가 보기에 구버전 팀명으로 표시되는 불일치가 발생합니다.

### C. 조별 리그(Group Stage) 진행 중 팀 데이터 결손
* 현상:
  * 24개 팀이 3개 조(A, B, C)로 나뉘어 순환 경기를 치르는 경우, 1일차 매치 데이터에는 당일 경기를 치른 16개 팀만 포함됩니다.
* 잠재적 오류 시나리오:
  * 1일차 데이터만 읽었을 때 "이 대회의 참가팀은 16개 팀이다"라고 잘못 판단할 수 있으며, 2일차 또는 3일차가 되어야 비로소 나머지 팀이 API에 나타납니다.

### D. 대회별 배점 룰셋(SUPER 포인트 vs 특수 룰) 차이
* 현상:
  * 현재 파이프라인은 정규 SUPER 포인트(1위 10점, 2위 6점 등 + 1킬 1점)를 고정 적용하고 있습니다.
* 잠재적 오류 시나리오:
  * 과거 WWCD(치킨 룰), Smash 룰, 또는 이벤트 매치(국가대항전, 올스타전) 등 변형 룰이 적용된 대회에서는 점수 계산 알고리즘이 실제 공식 순위표와 불일치하게 됩니다.

### E. 네트워크 및 API 기술적 제약
* Rate Limit (HTTP 429):
  * 대규모 매치를 일괄 조회할 때 요청 수 제한으로 인해 수집 중단 위험이 상존합니다 (지수 백오프 필수).
* 서버 튕김 및 재경기(Rematch):
  * 대회 중 버그나 서버 문제로 라운드가 무효화되고 재경기가 열릴 경우, API 상에 무효 매치와 정상 매치가 중복 존재하여 점수가 2배로 계산될 위험이 있습니다.

### F. 비공식 / 비인가 대회 데이터의 부재
* 크래프톤 공식 e스포츠 서버 shard(`tournament`)에 등록되지 않는 스크림(연습경기), 사설 스폰서 컵, 아마추어 클랜전 등은 API 자체가 제공되지 않습니다.

## 4. 무결점 자동화를 위한 4계층 보완 아키텍처 제안

1. 1계층 (원천 데이터 수집):
   * 공식 PUBG API를 통해 실시간 매치 원시 데이터(`primary_data`) 수집 (지수 백오프 적용).
2. 2계층 (지능형 닉네임 및 팀명 정규화 엔진):
   * 팀명 별칭(Alias) 사전 및 매핑 레이어 구축 (`Qx` -> `HSD`, `DK` -> `Dplus KIA` 등).
3. 3계층 (대회별 룰셋 템플릿 엔진):
   * 토너먼트 ID 접두사별로 적용 룰셋(SUPER, Smash, 치킨 룰) 및 참가팀 규모(16팀, 24팀)를 동적 주입.
4. 4계층 (이상 징후 유효성 검증기):
   * 매치당 16개 팀 초과/미만 발생 시 경고 발생, 재경기 플래그 감지 로직 적용.

## 5. 결론

단순히 API 엔드포인트 하나만 긁어오는 방식으로는 팀명 변경(리브랜딩)이나 조별 미출전 팀 누락 등의 예외를 100% 피할 수 없습니다.
그러나 "공식 API 원천 데이터" 위에 "지능형 팀명 매핑 레이어"와 "대회 룰셋 템플릿"을 결합한 다층 구조를 적용한다면, 어떤 공식 대회든 99% 이상의 높은 정확도와 실시간성으로 무결점 자동 최신화가 가능합니다.
